# OpenClaw: installation on AiBeast and pitfalls met

OpenClaw is an agent (web interface + gateway) that talks to your local Ollama. Installed on the reference machine on
21 October 2026 (version **2026.10.5**), next to the stack, in `~/openclaw`. This document keeps track of what was done,
what caused problems and what remains to settle.

## In short

- Installation: `cd ~/Documents/ai-lab && ./openclaw/install.sh` (**without** `| tee`: the wizard needs a real terminal).
- Interface: `http://127.0.0.1:18789/` (SSH tunnel, port 18789), token `OPENCLAW_GATEWAY_TOKEN` in `~/openclaw/.env`
  (do not share it).
- Container: `openclaw-openclaw-gateway-1` (the Docker project name, `openclaw`, is prepended to the service name).
- Model: `ollama/qwen3.8:27b-64k` (the 64,000-token version created by `lab dev ctx64`), context actually served: 65536.
- Configuration and data: `~/.openclaw` (seen as `/home/node/.openclaw` in the container).

## What was done

1. `./openclaw/install.sh`: clones `https://github.com/openclaw/openclaw` into `~/openclaw`, copies
   `docker-compose.override.yml` (the gateway joins `llm-net`), then runs the official wizard `scripts/docker/setup.sh`.
2. Answers to the wizard: provider **Ollama**, mode **Local only**, URL `http://ollama:11434`, model typed by hand;
   messaging channels (Discord, Telegram, WhatsApp…): **Skip for now**; web search engine: **Skip**. The wizard sets
   `gateway.mode=local` and `gateway.bind=lan`.
3. Dummy API key for the `ollama` provider (see below): `ollama-local`.
4. Default model set to `ollama/qwen3.8:27b-64k`, and the `contextTokens` context cap raised from 32768 to 65536 for that
   model (see below).
5. Windows tunnel: `LocalForward 18789 127.0.0.1:18789` (included in the configuration generated by `lab client`; add it
   to the PC's SSH configuration if missing, then reopen the tunnels).

## Problems met and solutions

| Symptom | Cause | Solution |
|---|---|---|
| `Ollama could not be reached at http://ollama:11434` in the wizard | The official script calls `docker compose -f docker-compose.yml …`: by naming that file, Docker **ignores** `docker-compose.override.yml`, so the gateway and the wizard's container do not join `llm-net` | `docker network connect llm-net openclaw-openclaw-gateway-1` (and for the wizard's temporary container: `docker network connect llm-net $(docker ps --format '{{.Names}}' \| grep 'openclaw-openclaw-gateway-run' \| head -1)`); `install.sh` now does it after the wizard |
| `docker exec openclaw-gateway …`: "No such container" | The real name is `openclaw-openclaw-gateway-1` | Use that name, or `docker compose -f ~/openclaw/docker-compose.yml exec openclaw-gateway …` |
| The gateway restarts in a loop (`Up 5 seconds`); log: "Gateway start blocked: existing config is missing gateway.mode" | Incomplete configuration left by a first, failed attempt | `docker compose stop openclaw-gateway`, then run the installation again; the wizard sets `gateway.mode=local` back |
| "Onboarding needs an interactive TTY" | The installation had been run with `\| tee`, which removes the terminal | Run it again without `tee` (to keep a log: `script -q -c "./openclaw/install.sh" /tmp/openclaw-install.log`) |
| "AI access test failed: No API key found for provider "ollama"" | OpenClaw requires a key even for local Ollama | `docker exec -it openclaw-openclaw-gateway-1 openclaw models auth paste-api-key --provider ollama`, dummy value `ollama-local`; then `docker restart openclaw-openclaw-gateway-1` |
| First message: `401 Unauthorized` on **`https://api.openai.com/v1/responses`** | The chat used an OpenAI model, not Ollama (the stored default was `ollama/gemma4`, and the chat selector had another model) | `models set ollama/qwen3.8:27b-64k`, model chosen in the interface settings, no fallback model. The test message left the machine but was refused for lack of a key |
| `ollama ps` shows CONTEXT 32768 although the model has `num_ctx 65536` | OpenClaw stores for each model a `contextTokens` cap (32768) that it sends to Ollama, and which wins over the model's setting | Change the model's `contextTokens` in `~/.openclaw/openclaw.json` (gateway stopped, backup `openclaw.json.avant-64k`); check: `ollama ps` after a message shows `65536` |
| Errors at the end of the installation ("different PID namespace", "Failed to reset agents.defaults.sandbox.mode to off") | A temporary container reads the configuration while the gateway locks it | No effect seen on how it works; the state of the tools sandbox was not checked |
| Page unreachable from Windows | The open SSH tunnel did not forward port 18789 | Add `LocalForward 18789 127.0.0.1:18789`, close and reopen the tunnels; test: `Test-NetConnection 127.0.0.1 -Port 18789` |

## Settings that matter

- **Default model** (CLI, from `~/openclaw`):
  ```
  docker compose -f docker-compose.yml exec openclaw-gateway sh -lc 'node dist/index.js models status'
  docker compose -f docker-compose.yml exec openclaw-gateway sh -lc 'node dist/index.js models set ollama/qwen3.8:27b-64k'
  ```
  After a change: `docker restart openclaw-openclaw-gateway-1`, then check that `llm-net` contains both `ollama` and
  `openclaw-openclaw-gateway-1`.
- **Do not connect any hosted model account** (banner "Connect a verified AI model"): it would link an outside service.
  Only Ollama models are allowed (`agents.defaults.modelPolicy.allow: ["ollama/*"]`, see Security).
- **Thinking**: set to "Default"; Qwen models can think for a long time before answering. "Off" speeds up the answers.
- **VRAM**: the 64k version takes ≈ 21 GB (KV cache in q8_0). Do not leave ComfyUI running at the same time
  (`lab mode normal`).

## Security

- **Ports limited to `127.0.0.1`.** The official compose publishes 18789 (interface), 18790 (bridge) and 3978
  (messaging channels) on all interfaces, and the installation sets `gateway.bind=lan`. In `~/openclaw/.env`:
  `OPENCLAW_GATEWAY_PORT=127.0.0.1:18789`, `OPENCLAW_BRIDGE_PORT=127.0.0.1:18790`,
  `OPENCLAW_MSTEAMS_PORT=127.0.0.1:3978` (without changing the official compose), then recreate the gateway and
  `docker network connect llm-net …`. Check: `ss -tlnp | grep -E ':(18789|18790|3978)'` only shows `127.0.0.1`.
  `openclaw/install.sh` now does it (backup `.env.avant-localhost`).
- **Restricted tools and models.** The `full` profile (59 tools) is kept, including `exec` (commands in the gateway's
  container), but with:
  - `agents.defaults.modelPolicy.allow: ["ollama/*"]`: only Ollama models can be used;
  - `tools.deny: ["gateway", "automations", "nodes", "browser", "canvas", "computer", "mobile_ui", "group:web"]`: the
    agent can neither change the gateway, nor create scheduled tasks, nor drive a browser, a screen or devices, nor
    search the web;
  - `tools.elevated.enabled: false`: no execution outside the normal settings.

  Applied in one validated write, after a backup (`~/.openclaw/openclaw.json.avant-restrictions`):
  ```
  cd ~/openclaw && G="docker compose -f docker-compose.yml exec -T openclaw-gateway node dist/index.js"
  P='{agents:{defaults:{modelPolicy:{allow:["ollama/*"]}}},tools:{deny:["gateway","automations","nodes","browser","canvas","computer","mobile_ui","group:web"],elevated:{enabled:false}}}'
  echo "$P" | $G config patch --stdin --dry-run && echo "$P" | $G config patch --stdin
  ```
  Check: `$G config get tools`, `$G config get agents.defaults.modelPolicy`, `$G sandbox explain`.
  Rollback: `cp ~/.openclaw/openclaw.json.avant-restrictions ~/.openclaw/openclaw.json && docker restart openclaw-openclaw-gateway-1`.
  Seen on the reference machine: OpenClaw answers, and its selector only offers Ollama models.
- **Sandbox: `off`, on purpose.** OpenClaw's sandbox (`mode: all`) starts Docker containers: the gateway would need
  access to the Docker daemon, which would open the whole machine to it. The gateway already runs in its own container,
  without network access (isolation). Remaining risk: an `exec` command can read or change what the container sees,
  including `~/.openclaw` (configuration, gateway token, settings above).
- **No messaging channel** is configured (on purpose): anything arriving from outside can give instructions to an agent.
- The test message sent to OpenAI (refused) shows that a wrong model setting can send what you type to an outside
  service: after any change, check the active model.
- **No Internet access**: the gateway only reaches Ollama; every outgoing connection is blocked by `lab isolation`
  ([agent-isolation.md](agent-isolation.md)). A hosted model selected by mistake can therefore no longer send anything
  out.

## Update

`cd ~/openclaw && git pull && docker compose pull && docker compose up -d`, then **reattach** the gateway to Ollama
(`docker network connect llm-net $(docker compose -f docker-compose.yml ps -q openclaw-gateway)`): recreating the
container loses the attachment. Running `./openclaw/install.sh` again also does it. Then `lab isolation apply`.

## What is not verified

- **The quality of OpenClaw's answers** with this model has not been judged; only that it works (`chat.send`, answer in
  ≈ 11 s to the first message) was seen in the logs.
- **`contextTokens`**: the interpretation (cap sent to Ollama) is a deduction; it is supported by `ollama ps` (65536
  after the change) but not by OpenClaw's documentation. The change was made directly in `openclaw.json`; it is not known
  whether an update or the rediscovery of models resets it to 32768. If so, use the CLI's `config` command (not
  explored).
- **Semantic memory** is degraded (`memory_index_chunks_vec not updated — semantic vector embeddings unavailable`): no
  embedding model is configured. Not handled.
- `~/openclaw` and `~/.openclaw` contain credentials (gateway token): they are not included in the backups described in
  `docs/backups.md` (not verified).

## Agents mode: only one agent at a time

`lab mode agents openclaw` keeps OpenClaw (its gateway container is started if needed) and stops Open WebUI, n8n, Qdrant,
SearXNG, Kokoro, Tika, ComfyUI; Hermes sessions are then refused. `lab mode agents` (Hermes) stops the gateway instead.
`lab mode normal` restarts it. Details: [lab.md](lab.md). After a start by this mode, the container keeps its `llm-net`
connection (a stop/start does not remove it); this has not been checked on the real machine.
