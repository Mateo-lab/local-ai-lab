# Portal (home page)

A single page with a button per service, a **health light** (green = answers, red = does not answer) and **machine
metrics** (GPU, memory, disks). Folder: `portail/`. Tool: [Homepage](https://gethomepage.dev).

## Start

```bash
lab start portail          # or: cd portail && docker compose up -d
```
Address: **http://127.0.0.1:3010**

Prerequisites: `ai-stack` **and** `monitoring` started (they create the `ai-stack_ai-net`, `obs-net`, `mon-net` networks
that the portal joins). Otherwise Docker answers "network … declared as external, but could not be found": run
`lab start` first (it respects the order).

## What the page shows

| Group | Content |
|---|---|
| Interfaces | Open WebUI, n8n, ComfyUI, Qdrant |
| Engine and tools | Ollama, SearXNG, Kokoro, Tika (lights only) |
| Observability | Grafana, Prometheus, Langfuse |
| Agents (on demand) | OpenClaw (link, no light), Hermes (information card) |
| Machine | GPU (power, temperature, load, P-state, VRAM), RAM, system disk, `/data` disk |

The **light** is an HTTP request made from the portal's container to each service (`siteMonitor` option). A service
that is not started (ComfyUI, Langfuse) shows red: that is normal. **Langfuse is not started by `lab start`** and is not
installed until `./6-langfuse.sh` has run: its card stays red until then.

### OpenClaw and Hermes: why no light
- **Hermes** has no web interface (command-line agent, container started on demand by `./5-hermes.sh`,
  `restart: "no"`): there is nothing to probe, the card is informative.
- **OpenClaw** listens on `127.0.0.1:18789` **of the machine**, in its own Docker project. To probe it, the portal would
  have to join `llm-net` (network shared with Ollama and OpenClaw), which would break their isolation ("OpenClaw only
  sees Ollama"). Choice made: a link without a light. The port is in the tunnels generated by `lab client`
  (`LocalForward 18789` line): present in your PC's SSH configuration if you pasted it entirely.
- For a light without touching the networks, the clean solution would be a probe in `blackbox` or a dedicated alert
  rule: not done, because OpenClaw is not running permanently.

The GPU **P-state** is useful: `P8` = idle (≈ 20 W), `P2` = a program keeps the GPU in compute mode (≈ 120 W).
See `docs/remote-desktop-gpu.md`.

## Files

| File | Role |
|---|---|
| `portail/docker-compose.yml` | Homepage container, port `127.0.0.1:3010`, 3 external networks |
| `portail/config/services.yaml` | List of services, lights, metric cards |
| `portail/config/settings.yaml` | Title, theme, language, group layout |
| `portail/config/widgets.yaml` | Date/time and resources of the portal container |
| `portail/config/bookmarks.yaml` | External reference links |

After a change to a file in `config/`, Homepage reloads it by itself (otherwise `docker compose restart homepage`).

### Adding a service
In `services.yaml`, under a group: a name, `href` (address to open), `description`, `icon`, and `siteMonitor` (internal
address `http://container-name:port`). The container must be on a network the portal joins (`ai-net`, `mon-net` or
`obs-net`); otherwise add that network in `portail/docker-compose.yml`.

### Adding a metric
One card = one Prometheus query. Template: `url: http://prometheus:9090/api/v1/query?query=QUERY` (QUERY URL-encoded:
`*` → `%2A`, `{` → `%7B`, `"` → `%22`, `/` → `%2F`), `field: data.result.0.value.1`.

## Access from your Windows PC

A single double-click: see [`remote-access.md`](remote-access.md) (files in the `windows/` folder).
The tunnels carry the same port numbers, so the portal's links work identically on Windows.

## Security

- The portal is bound to `127.0.0.1` (nothing is exposed on the network).
- **No access to the Docker socket**: if the portal were compromised, it would not give root rights on the machine. That
  is why the lights go through HTTP and not through Homepage's Docker integration.
- `HOMEPAGE_ALLOWED_HOSTS` only allows `127.0.0.1:3010` and `localhost:3010`. If you change the tunnel port on the
  Windows side, add the new name to this variable.

## What is not done, and why

- **Readable addresses (`webui.aibeast`)** with a reverse proxy: not done. Each service stores its own address
  (Langfuse: `NEXTAUTH_URL`, n8n: `WEBHOOK_URL`, Grafana: `root_url`, Open WebUI cookies). Putting them behind a
  different name means reconfiguring them one by one, with a risk of a broken login. The gain (no longer remembering
  ports) is already covered by the portal.

## What is not verified

- The icon names (`open-webui.png`, `comfyui.png`…): if one is missing, the card is shown without an icon.
- The health paths: `n8n /healthz`, `qdrant /healthz`, `grafana /api/health`, `prometheus /-/healthy`,
  `langfuse /api/public/health` are the usual paths. `kokoro /docs` and `tika /tika` are pages that answer by default,
  to be confirmed.
- The metric cards: the metric names (`nvidia_smi_*`, `node_*`) come from the `nvidia_gpu_exporter` documentation. If a
  card shows "Error", open Prometheus (`:9090`) and type the metric name to see whether it exists under that exact name.
- `format: bytes` for the VRAM: the value arrives from Prometheus as text; if the display is wrong, switch to
  `format: float` with `scale: 0.000000000931` (bytes → GiB).
